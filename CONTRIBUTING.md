# Contributing

This is a small repository with a narrow purpose: the astro operations DaVinci Resolve does not ship with. The rules below exist so that the history stays readable and so that what is measured stays distinguishable from what is assumed.

---

## Language

**English only** — code, comments, documentation, commit messages, issues and pull requests.

The astro and Resolve communities are overwhelmingly English-speaking, and this toolkit fills a niche that has no other occupant. German would be the wrong barrier to entry.

## Branching: Gitflow

| Branch | Purpose |
|---|---|
| `main` | Released, tested states only. Never commit here directly. |
| `develop` | Integration branch, and the repository default. Feature branches start and end here. |
| `feature/<issue>-<shortname>` | One branch per issue, e.g. `feature/3-soft-sky-mask` |
| `bugfix/<issue>-<shortname>` | A fix for something already on `develop` but not yet released |
| `release/<version>` | Stabilisation before a release; merges into both `main` and `develop` |
| `hotfix/<shortname>` | Urgent fix straight off `main`, merges back into `main` and `develop` |

```
git switch develop
git pull --ff-only
git switch -c feature/12-star-mask-output
```

## Commits: Conventional Commits

Format:

```
<type>(<scope>): <subject>

<body — the why, when it is not obvious from the diff>

Closes #<issue>
```

**Types:** `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `style`, `perf`
**Scopes:** `dctl`, `macros`, `docs`, `examples`, `repo`

Subject in the imperative, no trailing full stop, ideally under 72 characters.

```
feat(macros): add AstroGradient Fusion macro
fix(dctl): clamp negative values before arcsinh in AstroStretch
docs(macros): update measured parameters after Fusion verification
```

## Pull requests

- Base branch is `develop`.
- Put the closing keyword (`Closes #12`) in the PR body **before** merging. GitHub evaluates it at merge time — adding it afterwards does nothing, and the issue stays open.
- Describe how the change was verified, not just what it does. For this repository that usually means: against which image, at which resolution, with which control values.

## Issues

Every open point is an issue — not a TODO comment in the code. Bugs that surface while testing in Resolve get filed as new issues, with the templates under `.github/ISSUE_TEMPLATE/`.

For a bug report, the working colour space is the single most useful field: the stretch maths assumes scene-linear data, and applying it to log data is by far the most common cause of "it looks wrong".

## Working on the tools

### DCTLs

The development cycle is fast: save the file, click *Update Lists* in Resolve's Color Management, and the change is live. No restart.

Two things to keep in mind when editing:

- **Do not change the parameter variable name** in `DEFINE_UI_PARAMS` — the first argument. Resolve matches saved grades on it. Labels, defaults and ranges can change; the ID cannot, or saved grades lose their values.
- DCTLs see one input image and one frame. Anything needing two images, a second pass or a reduction across the whole frame belongs in a Fusion macro or a Fuse. See [docs/limitations.md](docs/limitations.md).

### Fusion macros

`.setting` files are **not** written by hand or generated by a script. One wrong serialisation detail and the file fails to import, or imports incorrectly without it being visible. Build the graph in Fusion, group it, export it via *Create Macro*, then commit the exported file.

### Parameters are measured, not guessed

The parameter tables in [macros/README.md](macros/README.md) carry real numbers from real image material, with the measurement conditions written next to them. If you change a default, say what you measured it against — sensor, resolution, exposure. A default that works on 24 MP does not automatically work on 45 MP, and star-size-dependent values scale with star size in pixels, not with image size.

Anything not yet verified is marked as such. Keeping that boundary honest is more valuable than a confident-sounding number.

## Licensing

The project is MIT licensed, and it should stay permissively licensed.

**Do not copy code from GPL-licensed DCTL or Fuse collections**, however convenient — for example the widely used convolution collections. Where a kernel is needed, implement it. That constraint is deliberate and is the reason this repository can be used without licence friction.
